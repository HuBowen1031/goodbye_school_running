## F1 ★ σ 的舍入值被代入了后续计算

**涉及**：works.md §3.5 → §5.3 → §5.4

§3.5 的表把 1 Hz 的表观速度抖动显示为 `2.0 km/h`，这是**四舍五入后的显示值**。
但 §5.3 的安全带公式和 §5.4 的 golden 表，都把这个 `2.0` 当作**计算输入**继续使用。

精确值：

```
σ = √2 · √(d_slow² + d_fast²) / Δt
  = 1.9552 km/h        （1 Hz，真实档）
```

**由此产生的系统性偏移**：

| 量 | 用 σ=2.0（文档） | 用 σ=1.9552（精确） | 差 |
| --- | --- | --- | --- |
| 2σ 安全带下沿 | 10.152 | 10.061 | −0.091 |
| 2σ 安全带上沿 | 12.381 | 12.466 | +0.085 |
| 1σ 安全带下沿 | 8.122 | 8.076 | −0.046 |
| 1σ 安全带上沿 | 14.329 | 14.386 | +0.057 |

§5.4 各行的 `[v_lo, v_hi]` 也因此普遍偏 0.04–0.14。

**处置**：实现保留精确值（**显示层该舍入，计算层不该**）。
`tests/golden/estimate.json` 的 `tolerances.v_lo/v_hi` 设为 ±0.15 以容纳这个口径差，
并在 `_why_v_lo_wide` 里写明原因。

> 这不是 bug，是**精度纪律**问题。若将来要让 §5.4 与实现逐位对齐，
> 正确做法是把文档的 σ 列改成 `1.9552 (显示 2.0)`，而不是把实现改回 2.0。

## F2 ★ works.md §5.3 与 §5.4 对判定颜色的定义不一致

**涉及**：works.md §5.3 判定表 vs §5.4 判定列

§5.3 给出了**规则**：

| 条件 | 颜色 |
| --- | --- |
| `v_lo ≥ 6` 且 `v_hi ≤ 17` | 🟢 |
| 1σ 内安全、2σ 越界 | 🟡 |
| 其余 | 🔴 |

§5.4 的**示例表**里，9.0 / 13.0 / 14.0 三行被标为 🔴。但它们的 1σ 区间并没有越界：

```
9.0  ： 1σ 下界 = 9.0×0.985 − 1.9552 = 6.92 > 6      → 按规则应为 🟡
13.0 ： 1σ 上界 = 13.0×1.05 + 1.9552 = 15.61 < 17    → 按规则应为 🟡
14.0 ： 1σ 上界 = 14.0×1.05 + 1.9552 = 16.66 < 17    → 按规则应为 🟡
```

（对照：8.0 的 1σ 下界 = 5.88 < 6，确实越界，标 🔴 是正确的。）

**处置**：**规则定义优先于示例表**。

- 实现按 §5.3 判色（`safety_color`）。
- §5.4 的原值保留在 `tests/golden/estimate.json` 的 `doc_safety` 字段，不篡改。
- 分歧行登记在 `document_contradictions`，并由
  `TestGoldenTable::test_safety_disagreements_are_registered` 守住 ——
  将来若有人"顺手"改掉这些行，测试会失败。

**影响面**：只影响色带的黄/红边界，不影响 🟢 区间。
两种口径都指向同一可操作结论：**只有 [10.2, 12.4] km/h 才是真正安全的**。

## F4 折线拐角会让 `v_actual` 产生几何抖动

**性质**：这不是文档问题，是**建模的固有性质**，但会误导测试断言。

`v_actual` 由相邻两点的**大圆距离**除以时间间隔得出。
在路线的直角拐角处，两点间直线距离小于沿路线的弧长，于是该点的 `v_actual` 会偏低。

实测（3 km，10 km/h，1 Hz，**关掉所有随机噪声**）：

```
v_actual  stdev = 0.2076 km/h
v_actual  range = 7.338 .. 10.335 km/h
```

其中 7.338 是起步 ramp 段的真实低速，而 stdev 的 0.2 里有相当一部分来自拐角。

**处置**：`test_off_has_much_less_jitter_than_realistic` 用
「关噪声的抖动 < 0.8，且至少比真实档小 2.5 倍」这种**相对**断言，
而不是给绝对阈值 —— 后者会被路线形状偶然影响。

## F5 AR(1) 样本方差对长相关序列有系统性负偏差

**性质**：统计估计量的性质，不是实现问题，但会让噪声测试"无故"失败。

对 AR(1)，样本方差的期望：

```
E[s²] ≈ σ² · [1 − (1/n)·(1+ρ)/(1−ρ)]
```

而 `(1+ρ)/(1−ρ) ≈ 2τ/Δt`（当 Δt ≪ τ 时）。所以

```
E[s²] ≈ σ² · (1 − 2τ/T)
```

慢分量 `τ = 300 s`：

| 观测时长 T | σ 的低估幅度 |
| --- | --- |
| 4 000 s | 15.0% |
| 8 000 s | 7.5% |
| 20 000 s | 3.0% |

首次跑测试时，用「单种子 20 000 点」估计 σ，得到 `2.67` 而非 `3.015` ——
**正好落在这条偏差线上**。

**处置**：`tests/test_noise.py::_ensemble_sigma` 做了两件事：

1. **多种子平均**（慢分量导致有效独立样本只有 ~67 个）；
2. **按分量加权解析修正**偏差因子 `1 − 2τ/T`。

这样容差可以收紧到 ±10%，而不是靠"拍脑袋放宽"过关。

## F6 `η(t)`（呼吸/路况速度波动）在初版实现里被漏掉了

**涉及**：works.md §3.2 剖面表

§3.2 明确列出了 5 个剖面分量，其中：

| 分量 | 参数 |
| --- | --- |
| `η(t)` 呼吸 / 路况引起的速度波动，AR(1) | `σ_v = 0.35 km/h`，`τ_v = 10 s` |

初版 `SpeedProfile` 只实现了 ramp / drift / finish / clamp 四项，
`speed_at()` 虽然**接受** `eta` 参数，但 `TrackEngine` 从未传入 —— 即 η 恒为 0。

**处置**：补上 `SpeedProfile.sigma_v / tau_v` 字段与 `noise.SpeedJitter` 类。

设计上的一个刻意选择：**η 与 GPS 位置噪声走两条独立的随机流**。

- 位置噪声描述「**测量误差**」，η 描述「**跑者速度的自然起伏**」—— 物理来源不同；
- 混在一条流里会让「换个噪声档位」意外改变速度剖面，并让 §3.5 的表观抖动口径含糊；
- 但两者都从同一个人工种子经偏移派生，所以「同种子 ⇒ 同轨迹」依然成立。

**副产品**：η 是零均值波动，会让实测 ETA 产生 ±4 s 左右的**合法**抖动
（`ΔT/T ≈ −η̄/v̄`，`σ(η̄) ≈ σ_v·√(2τ_v/T)`）。
因此「实测 ETA 与预测一致」这类验收测试必须先 `eta_sigma=0.0` 关掉 η，
否则测的是运气而不是一致性。

## F8 ★ `simulate-location set` CLI **永久阻塞** —— 逐点注入在 CLI 层面不可能

**涉及**：works.md §4.1「为什么不用 CLI 子进程逐点注入」

works.md 给出的理由是：

> CLI 每次启动开销 300–800 ms，1 Hz 都稳不住。必须用**常驻进程的 Python API**。

**实测（2026-10-12，生死验证 1）发现真实原因比这强得多。** 读 `cli/developer/dvt/simulate_location.py`：

```python
@cli.command("set")
@async_command
async def dvt_simulate_location_set(service_provider, latitude, longitude) -> None:
    async with DvtProvider(service_provider) as dvt, LocationSimulation(dvt) as location_simulation:
        await location_simulation.set(latitude, longitude)
        OSUTILS.wait_return()        # ← 设完就永久阻塞，等 Ctrl-C
```

而 `clear` **没有**这一行：

```python
@cli.command("clear")
@async_command
async def dvt_simulate_location_clear(service_provider) -> None:
    async with DvtProvider(service_provider) as dvt, LocationSimulation(dvt) as location_simulation:
        await location_simulation.clear()      # ← 设完就退出
```

**后果**：

1. `set` 不是「设完就走」的命令，而是一条**必须常驻**的命令 ——
   它要靠 `async with` 保持 DVT 连接存活，进程一退出上下文就析构。
2. 因此 **CLI 层面根本不存在「循环注入」的形态**。
   works.md 说的「启动开销 300–800 ms」是**次要**理由；
   就算开销是 0，这条命令也用不了 —— 它一次只能设一个点然后就卡住了。
3. 实测印证：`set` 发出后一直不返回，120 s 后被 harness SIGTERM（`Terminated: 15`）；
   `clear` 则立即返回、无输出。

**结论不变，理由要换**：

> ✅ 「必须用常驻进程的 Python API」—— **works.md 的决策是对的**
> ⚠️ 但支撑它的理由不完整。若按原理由去质疑这个决策
> （"优化一下启动开销不就行了？"），会得出错误结论。
> **真实理由是结构性的：CLI 没有循环形态。**

**处置**：

- M2 的 `DeviceBridge` 必须是**常驻进程**（works.md §4.2 已是此设计，此条只是补上硬证据）；
- 逐点注入循环要自己写，仿照 `LocationSimulation.play_gpx_file()` 的思路
  （works.md §1.2 已指出该函数「本质是按时间戳 sleep 后循环 set()」）；
- `clear` 可以安全地用作**独立的一次性进程**，因为它不阻塞 ——
  这是 `scripts/panic-clear.sh` 的技术前提。

> 附带确认 works.md §1.2 的另一条：`LocationSimulation` 只有
> `set(latitude, longitude)` 与 `clear()` 两个方法，
> **确实没有** speed / course / altitude / timestamp。§2.1「时间不可伪造」的前提再次坐实。

## F9 ★ 存在一条比 `device.py` 更省的注入路径（但不完整）

**涉及**：works.md §4.2「M2 设备桥」的设计取舍

works.md 规划 M2 写 `device.py` 封装 `LocationSimulation`，
在**常驻进程**里自己写循环逐点 `set()`。

**2026-10-12 实测发现**：这个循环**不用写** —— 上游已经提供了：

```bash
vrun gpx --route X.json --speed 10 --out logs/run.gpx     # ① M1 离线算轨迹
pymobiledevice3 developer dvt simulate-location play -- logs/run.gpx   # ② 回放到真机
```

`play_gpx_file()` 内部就是「按 `<time>` 差值 sleep → 循环 `set()`」，
一份带时间戳的 GPX 就是一条完整轨迹。**实测 166 m / 66 s / 9–10 km/h 一次跑通，
校园 App 计数正确、零告警。**

### 为什么这条路径值得单独记

| | `play` 回放（现成） | 自写 `device.py` |
| --- | --- | --- |
| 隧道 / DVT 连接管理 | **上游包了** | 自己写（lockdown → RemotePairing → tunnel → RSD） |
| 轨迹一致性 | **离线算的与注入的逐字节一致** | 实时算，时钟抖动会进入轨迹 |
| 中途改速度（§5 滑块） | ❌ **做不到** | ✅ |
| 暂停 / 恢复 | 杀进程 + clear + 从当前位置重生成 | ✅ |
| 实时遥测回 GUI | ❌（但轨迹是我们自己算的，本就知道） | ✅ |

### 结论：**两条都要，但不是替代关系**

- **`play` 覆盖「跑一次完整会话」** —— S2 冒烟检查（works.md §7.2）用它就够了，
  而且零维护成本。M4 的验收可以现在就做，不必等 M2 写完。
- **自写 `device.py` 只为一件事：§5 的速度滑块** —— 「跑到一半改速度」
  在 `play` 模型下不存在，因为轨迹已经是固定文件了。

> ⚠️ 换句话说：**M2 的必要性从「能注入」降级为「能中途改参数」**。
> 这不改变里程碑顺序，但显著改变了 M2 的**风险等级** ——
> 它不再是「不做就什么都做不了」，而是「不做就只有静态轨迹」。

> 附：`play` 回放完同样落在 `OSUTILS.wait_return()` 上永久阻塞（F8 同样适用于 `play`），
> 所以进程回收仍是必需的。三保险（works.md §2.3）对它一视同仁。

## F10 闭式解与精确积分的 0.76 s 偏差会翻转**显示的秒数**

**涉及**：works.md §3.6 闭式解、§5.4 基准表、§5.6 「预览 vs 精确」自检

**发现方式**：写 Swift 跨语言契约测试（`PreviewMathTests`）时，
把 `closedFormEta` 拿去逐行比 §5.4 表格的「修正 ETA」列，12.4 km/h 那行对不上。

**根因**：比错了列，但暴露了一个真问题。

| | 12.4 km/h @ 3 km |
| --- | --- |
| 纯运动 | 870.97 s |
| 闭式解（§3.6，GUI 拖动时用） | **878.76 s** → `Int(round())` → 879 → **14:39** |
| 精确积分（Python `expected_duration`，权威） | **878.0 s** → 878 → **14:38** |

两侧**公式一字不差**，差的 0.76 s 是一阶近似本身的残差。
问题不在精度，而在**取整边界**：878.76 离 878.5 只有 0.26 s，
于是「预览 14:39 / 实测 14:38」这种 1 秒的可见不一致真的会发生。

**为什么 §5.6 的自检抓不到**：§5.6 规定差值 > 1 s 时 GUI 高亮提示。
这里差 0.76 s < 1 s，**不触发提示**，但显示值确实差了一格。

**处置**（已落实）：

- 测试改成**秒级容差断言**（`|闭式解 − 精确| ≤ 1 s`），不再断言文本相等 ——
  文本相等在取整边界上是脆的，容差才是真正的契约。
- 新增 `testF10RoundingBoundaryAtTwelvePointFour`，把这个已知偏差**钉死**为
  878.76 s / 「14:39」。谁改动闭式解，这条测试会立刻报出来。
- 12.4 行在文本断言里显式排除，并注明原因（与 F3 对 17.0 行的处理一致）。
- GUI 行为**不变**：14:39 是闭式解的诚实输出，实测值由侧车的 `eta_s`（精确积分）
  在松手后替换，用户看到的最终读数仍是 14:38。预览与实测的秒级差异属预期。

> 顺带说明：§5.4 表格那一列是**精确积分**，不是闭式解。
> 这一点原来没写清楚，是本次做契约测试时才发现的 —— 已在本条记录备案。

## F11 ★ 会话层有三个 bug，**只有写单测才能抓**（真机验不出）

**涉及**：works.md §6 M2 的 `session.py`

6 点真机移动测试**通过了**（蓝点跟着走、清理正常）。
但那**只证明了设备层通**。把引擎接上去写会话层时，单测连着揪出三个 bug ——
它们的共同点是：**真机上跑 18 分钟也未必看得出，单测一秒就炸**。

### ① ★★ 会话从头到尾没有注入过任何位置

`_on_sample_blocking` 只发 tick / progress 事件，**根本没调 `set_location`**。

后果极其隐蔽：tick 照发、progress 照报、状态机照跑、统计照算 ——
**一切看起来都正常，但手机上一个点都不会动**。
真机上要发现它，得先等 18 分钟跑完、再去翻 App 的记录看距离为 0。

> 钉它的测试就是背压那条：断言「tick 数 == 注入数 == 采样点数」。
> 用 `+1` 的**精确式子**而不是 `>=` —— 少算 `prepare()` 那次就会差 1，
> 而这个差 1 正是漏调的信号。

### ② `stop()` 先等线程、后置状态 —— 「停止」要等整条路线跑完

`_sleeper` 靠检查 `phase` 决定该不该退出，但 `stop()` 写的是
「先 `await _wait_task()`，再把 phase 改成 STOPPED」。
于是引擎看到的永远是 RUNNING，**停止信号根本到不了它**。

真机上点「停止」，实际效果是**再等 18 分钟**。

> 解法：拆出一个独立的 `_stop_requested` 标志，`stop()` 先置它再等线程。
> 刻意**不与 `phase` 合并** —— `phase` 是对外报告的状态，
> `stop()` 执行的那一刻它本来就该还是 RUNNING。合成一个字段会让「停止」重新失效。

### ③ 保险注册是**进程级**的，测试里必须显式收摊

`SafetyGuard.arm()` 注册的 `atexit` 与 signal 处理器**不随对象消亡**。
十几条会话用例各 arm 一次，就等于在解释器退出时起十几个真子进程去连真机 ——
套件尾部静默挂几十秒，报错点还落在「测试全部跑完之后」，
看起来就像 pytest 本身卡死了。

> 正常流程里保险本来就该留到最后，所以这不是 bug；
> 但测试里必须拆。加了一个 autouse fixture 追踪所有 arm 过的 guard 并收摊。

**共同教训**：这三类 bug 的可观测性都很差 —— 失败时**没有报错、没有异常、日志正常**。
唯一可靠的抓法是**把不变量写成断言**（注入数 == 采样点数、状态迁移的顺序、进程级副作用的收尾）。
这也是为什么 `test_session.py` 的重点不是「跑通一次」，而是「跑了很多次之后状态仍然自洽」。

## F12 ★ 一条单测在**偷偷连真机**，表现为「随机的」套件卡死

**涉及**：`tests/test_device.py::test_boundary_coordinates_accepted`

### 症状

同一个测试套件，连着跑两次：

- 第一次：`293 passed in 20.96s`
- 第二次：挂住 > 60 s，杀不掉

单独跑 `tests/test_session.py`：23 条全过。
单独跑全量带 `-v`：稳定停在 `test_boundary_coordinates_accepted` 这一条上。

**没有任何报错、没有异常、日志正常** —— 和 F11 属于同一类可观测性陷阱。

### 根因

`DeviceBridge.set_location()` 的结构是「**先校验，再连接，再注入**」：

```python
if not (-90.0 <= lat <= 90.0):          # ← ① 校验闸门
    raise ValueError(...)
await self.connect()                     # ← ② 真正的硬件动作
```

而这条测试要验的恰恰是「**±90 / ±180 是合法边界，不能误拒**」——
坐标合法，于是它一路穿过 ①，直奔 ②。

`test_device.py` 里其余测试都安全：它们只碰 `clear()` / `aclose()` / `status()`，
这三个都**不触发连接**；参数非法的那些在 ① 就被拒了。**只有这一条会走到 ②。**

### 为什么表现得像「随机抖动」

结果完全取决于手机在不在线：

| 手机状态 | 表现 |
| --- | --- |
| 没插，或 usbmuxd 查不到设备 | 快速抛 `DeviceNotFound` → 测试「通过」 |
| 插着 | usbmuxd 找到设备 → 真的去建隧道 → **整个套件挂死** |

于是「手机插上再跑测试」这件事本身，就成了触发条件。
而套件 293 条用例跑完只要 20 s，一个真的在建隧道的连接足以把整个进程钉住。

### 处置

加 `validation_only_bridge` fixture：把 `connect()` 换成空实现 + 一个假注入器
（只提供 `async set(lat, lon)` 的桩）。校验闸门一个不差地被覆盖，硬件彻底隔离在外。

顺带把断言改严了 —— 原来那个 `except Exception: pass` 会把「连不上设备」
和「校验通过」混为一谈，现在直接断言边界坐标**确实进了注入器**。

### 顺带核实的一件事（**结论：没问题**）

`device-status` 会调 `bridge.connect()`，看上去「一个状态查询却武装了手机定位」。
查 pymobiledevice3 源码确认：`DtxService.__aenter__` **只开 DTX 通道**，
真正武装定位的是 `simulateLocationWithLatitude:longitude:`（即 `set`）。
所以 `connect()` 本身不动手机的定位状态，`aclose()` 里那句 `clear()` 只是保险。
**这是核实后的结论，不是「看起来没问题」** —— 写在这里免得下次再怀疑一遍。

### 教训

「设备层单测不得碰真机」这条纪律，光靠**逐个测试检查**是守不住的 ——
`set_location()` 里校验通过就会连设备，这个副作用对调用方是不可见的。

有效的护栏是**在 fixture 层面把硬件换掉**，让「忘了加 fixture」这件事
在物理上不可能发生 —— 而不是指望每个测试作者都记得。

> 对照 F7（侧车解释器解析）：那次的 bug 也是「单测全绿但实际会失败」，
> 同属「测试环境与生产环境不一致」这一类。两次的抓法都是**让测试跑在真实形态上**。

## F13 ★ 崩溃栈顶的符号**不是**真凶；纯逻辑测试对框架内部抛异常完全无能为力

**涉及**：`app/VRun/Sources/VRunApp/RouteCanvas.swift`（`GreenDotAnnotationView`）、
`app/VRun/Tests/VRunAppTests/GreenDotMapKitTests.swift`（新增）

### 症状

GUI 一改完就出现「点一下地图，进程 abort」。崩溃报告（`asiBacktraces`）逐帧是：

```
objc_exception_throw
-[MKAnnotationView clusteringIdentifier]            ← 栈顶
-[MKMapView addAnnotationRepresentation:allowAnimation:]
-[MKAnnotationManager updateVisibleAnnotations]
-[MKMapView _didChangeRegionMidstream:]
-[MKMapView mapLayerDidChangeVisibleRegion]
VectorKit -[VKMapCameraController _animateToPosition:…]
-[MKMapView setCenterCoordinate:animated:]          ← 就是 updateNSView 里那一行
RouteCanvas.updateNSView(_:context:)
```

主线程栈显示 `-[NSApplication _crashOnException:]`，没有任何 reason 字符串。

在此之前，钢笔与绿圈一共有 **26 条测试，全绿**；编译零警告；加点数据全对；
连 `animated: false` 都改过了。**三件事同时成立，进程照样死。**

### 根因

`canShowCallout = true`，而 `DeviceAnnotation` 没有 `title`：

```
<…DeviceAnnotation: 0x…> must implement title, or view must have a
non-nil detailCalloutAccessoryView when canShowCallout is YES (NSGenericException)
```

MapKit 在把 annotation 装配成 view 时抛 ObjC 异常，没人接 ⇒ `abort()`。

### 两次**错误**的归因（都记下来，因为它们各自都"有证据"）

**其一：把栈顶符号当成了真凶。**
`clusteringIdentifier` 正好是头文件里写着「留给子类实现」的属性，
看着就是标准答案。于是去覆盖 getter。**但变异测试证明这是错的** ——
把 getter 覆盖删掉、只留 `init` 里的 `clusteringIdentifier = nil`，5 条测试照样全绿。
赋值本身就等于「实现」了这个属性。

**其二：把崩溃归给了 `animated: true` 的定时器交错。**
2026-10-14 早些时候把 `setCenter` / `setVisibleMapRect` 全改成 `animated: false`，
理由写的是「动画期间 MapKit 在 `VKTimedAnimation` 定时器回调里重装配标注，
与 SwiftUI 的下一轮 `updateNSView` 交错」。重读崩溃栈才发现：
**即使 `animated: false`，`setCenter` 也是同步走完同一条链的**
（`setCenterCoordinate:animated:` → `_animateToPosition:` → `mapLayerDidChangeVisibleRegion`
→ `updateVisibleAnnotations`）。整套「定时器交错」的解释都不成立，
无动画只是顺手绕开了另一条不稳定路径。

顺带澄清一个被当成独立 bug 的现象：**「第 2 次加点不重绘」和这次闪退是同一个 bug**。
第 1 次加点确实重绘了（日志可证 `MainView.body 求值 route=1`），
紧接着 `updateNSView` 里的 `setCenter` 把进程带走 —— 于是第 2 次点击打在死进程上。
前期为此折腾过 `@Published` 通知、`@MainActor` 隔离、观察链转发，
方向全错：**先分清「界面没更新」和「进程已经没了」。**

### 处置

1. `canShowCallout = false`，去掉那个 `target: nil, action: nil` 的死按钮
   （绿圈只是「起点」的视觉标记，本来也不需要交互）。
2. 新增 `GreenDotMapKitTests.swift`：把绿圈**真塞进带窗口的 `MKMapView`**，
   走一遍 `addAnnotation` + `setCenter`。
3. 修正 `RouteCanvas.swift` 里三处**已经站不住的注释**（动画交错、必须覆盖 getter、崩溃栈顶符号）。
   错误的原因比没有原因更贵 —— 它会把下一个人引到同一个坑里。

### 两条测试纪律

**其一：纯逻辑测试证明不了「框架会接受这个对象」。**
点击判定、锚点取值、`@Published` 通知，全都是我们自己写的逻辑，
而 abort 发生在 **MapKit 内部** —— 纯逻辑测试根本没有能力覆盖那一层。
只要往 MapKit / AppKit 这类框架里塞对象，就必须有一条真把对象交给框架、
让它走一遍内部装配路径的测试。

**其二：XCTest 会把 abort 变成可捕获的异常，于是能拿到 reason。**
裸跑只看到一个没有 reason 的 `abort`；放进测试里，MapKit 的原话直接印在失败信息上。
**这正是「测试能问出框架为什么不接受」的唯一途径。**

写这条集成测试时还踩了一个更隐蔽的坑，记在测试文件里：
`MKMapView.delegate` 是 **`weak`**。写成 `map.delegate = Coordinator(...)`
的话 Coordinator 当场析构 ⇒ MapKit 走默认路径 ⇒ **永不崩 ⇒ 测试假绿**。
必须用局部强引用把它按在生命周期里。这条已经写成
`test绿圈的view确实被MapKit取走过` 这条护栏测试常驻。

## F14 ★ 跨语言协议两侧**都不报错**：`Decodable` 成功不等于字段对上了

**涉及**：`app/VRun/Sources/VRunApp/Models.swift`（`SidecarEvent`）、
`app/VRun/Sources/VRunApp/SessionController.swift`（`apply(_:)`）、
`tests/golden/session_events.json`（新增）、`tests/test_session_golden.py`（新增）

### 症状

M3 的「实时视图」一直没人实现，但查下去发现**不是缺功能，是有一条一直在发、
但从来没被接过的数据线**：

- `session.py` 从 M2 落地起就一直按 1 Hz 发 `tick` + `progress`
- Swift 侧 `SidecarEvent` **压根没声明** `t / s / v_target / v_actual / sigma_v / …`
- `SessionController.apply(_:)` 里 `if ev.event == "device"`，
  其余事件连看都不看

后果：会话进行中，GUI 的 HUD 只有一个「进度：开始推进…」，
已走距离、用时、瞬时速度、抖动**一个都没有**。
而 M4 要做的「比对预览 ETA 与实际用时」，在这种情况下只能靠翻日志文本。

**全程零报错。** 编译干净、Python 侧照发、Swift 侧 `Decodable` 照成功。

### 为什么两侧都沉默

因为 `SidecarEvent` 的字段全是**可选**（`let t: Double?` 这种）。
`Codable` 的约定是：**JSON 里没有的键，解出来就是 `nil`，不算错**。
于是「Python 发了一个字段」与「Swift 压根不知道有这个字段」这两件事，
在运行时**完全无法区分**。

顺带一提：当时还挂着一个 `@Published var tick: (t, lat, lon, s)?`，
**从来没被赋过值**，是个死字段 —— 它让人以为「tick 已经被处理过了」。

### 处置

新增 `tests/golden/session_events.json`：**真跑一小段会话**（假设备、不碰硬件）
抓下第一个 `tick` 与第一个实时 `progress`，两侧都对着它写：

| 侧 | 文件 | 验什么 |
| --- | --- | --- |
| Python | `tests/test_session_golden.py` | 载荷的**键集合**与基准严格相等 |
| Swift | `LiveMetricsTests.swift` | 真去**解码**那份 JSON，数值逐字相等 |

比对**键集合**而不是逐值相等：浮点会随 numpy 版本合法地漂一点，
而**键名对不上才是真正的契约破裂**。

变异验证（协议漂移会不会被抓到）：
给 `tick` 多塞一个 `elevation` 字段 → Python 侧红，报出「基准 vs 实际」的键差异；
把 Swift 的 `case sigmaV = "sigma_v"` 拼成 `"sigma_V"` → **3 条 Swift 测试红**。

### 三条可复用的纪律

**其一：`Decodable` 成功 ≠ 字段对上了。**
可选字段的解码永远不会失败，所以「解码成功」这个信号在协议一致性上**零信息量**。

**其二：跨语言协议必须有「**双方共用的真实载荷**」。**
注意是**真实**——不是照着头文件手抄一份。`PreviewMathTests` 那种
「把 golden 的数值转抄进 Swift 测试」的写法在这里会**重演同一个 bug**：
转抄本身就是一次人工搬运，而这次 bug 的本质就是搬运没发生
（压根没想到要搬）。所以 Swift 侧直接读那份 JSON。

**其三：注册一个协议 wart，而不是顺手改协议。**
`progress` 事件名被**重载**了：`run.prepare` / `run.start` / `run.stop`
的应答（会话摘要）与 1 Hz 实时指标同名，载荷形状却不同 ——
现在靠「`sigma_v` 在不在」区分。

拆成两个事件名显然更干净，但那是**改协议**，会影响 Python 侧与已有文档。
在没有实测依据、也没有第二个消费方的情况下改它，属于超出问题范围的改动 ——
所以这里只登记、只给消费侧加测试守住这个约定
（Python 侧 `test_progress确实被重载…`），把决策留给真正要动协议的时候。

⚠️ 消费侧必须显式写判别式。写成 `case "progress":` 就完蛋：
GUI 会把「会话刚开始，这是摘要」当成一条实时读数，
显示出一个不动的 0 km/h —— **比不显示更难查**。

## F15 ★ 压测工具本身也会骗人：「await 回来了」不等于「跑完了」

**涉及**：`src/vrun/soak.py`（新增）、`src/vrun/device.py`（新增 `InjectionStats`）、
`tests/test_soak.py`（新增）

### 背景

M2 短测只有 6 个点、每点停 3 s。它证明的是「**能注入**」，
不是「18 分钟不漂、不漏、不卡」—— 而 M4 的 3 km 全程恰恰是 18 分钟。

works.md §6 M2 那条「实测 1 Hz 连续注入 10 分钟，统计丢失点数与**延迟分布**」
当时只落了 ``dropped`` 计数器，延迟分布这一半**没有埋点**。

### 写压测工具时踩到的三件事

**其一：`strict=True` 意味着单点失败会让整个会话中断。**

`RunSession._on_sample_blocking` 用的是 ``_submit_coro(..., strict=True)``，
所以注入失败**不是**「跳过一个点继续跑」，而是当场把引擎打挂。

⇒ 这修正了一个此前的表述：`DeviceStatus.dropped` 的注释写「非零说明轨迹有洞」，
实际上它非零时**会话已经失败了**。两者都成立，但只有后者是真的行为。
于是压测里 ``dropped > 0`` 必然同时伴随三件事：会话提前结束、一条 ``error`` 事件、
覆盖时长不够。测试把这一条钉住了。

**其二：`RunSession._wait_task()` 最多只等 5 秒。**

它内部是 ``wait_for(shield(task), timeout=5.0)`` —— 引擎还在正常跑时，
它 5 秒后就返回了。

我的压测 harness 一开始写成「先 `_wait_task()`、再等到点、再清理」，
于是 5 秒后就进了清理，而**引擎线程仍在后台注入**。
真机上那表现为：手机最终停在**压测途中**的某个点而不是回到真实 GPS，
而报告还写着「清理已确认」。

⇒ **清理必须在引擎线程真的退出之后做。**
正确顺序是「先等到点触发 `stop()`（它内部会等线程）、再兜一次 `_wait_task()`」。

⚠️ 顺带修掉这个 wart 本身：新增 :meth:`RunSession.wait_until_finished(timeout)`。
原来的 ``_wait_task`` 是**会话内部的快路径** —— 调用它之前（``stop`` /
``cleanup``）已经先置了停止标志，引擎一两个采样周期内就会退出，所以 5 秒足够、
它**故意不等**。但外部要等「一次 18 分钟的运行自然跑完」时 5 秒显然不够。
新方法只做这一件事，不改 ``_wait_task`` 的语义（改了会波及 stop / cleanup）。

**其三：失败信号要从 ``error`` 事件接，不能靠 `try/except`，也不能事后查 `phase`。**

- ``try/except`` 没用：`_run_engine_blocking` 把引擎异常**吞掉**并转成 ``error`` 事件
  （这是有意的 —— 不让工作线程静默死掉，否则 GUI 会一直停在「运行中」），
  异常根本不会冒到调用方。
- 事后查 ``phase`` 也没用：它确实被置成了 ``FAILED``，
  但**紧接着的 `stop()` 又会改回 `STOPPED``** —— 查的时候已经看不到了。

⇒ 只有 ``emit`` 回调里的 ``error`` 事件是可靠的失败信号。

### 处置

- `device.py` 新增 `InjectionStats`：记录**每一次尝试**的耗时（含失败与超时）。
  只记成功的话，看到的分布会很漂亮，而真出问题的那次被抹掉了。
  **刻意不塞进 `DeviceStatus`** —— 那是每秒推给 GUI 的快照，
  塞进增长型列表等于每秒重传一遍历史。
- 新增 `vrun soak --minutes N`：无头运行（不走 GUI、不需要点按钮），
  产出「丢失点数 + 延迟分位数 + 覆盖时长 + 清理确认」四件套。
- 判定红线四条，缺一不可：**丢失点数 = 0、跑满计划时长、无报错、清理成功**。

### 为什么给压测工具写这么多测试

一份把「丢了 40 个点」显示成「✅ 通过」的报告，**比没有报告更坏** ——
它会让人以为验证过了。所以 ``report_lines`` 的每个判定分支都有用例，
而且做了 5 组变异验证（去掉任一条红线、去掉 panic-clear 提示、
不再接 error 事件、阈值形同虚设），确认测试真的在守。

⚠️ 变异⑤第一轮**没被抓到**：那时只有两条相关用例，
而其中一条的 ``error`` 非空会把阈值判断短路掉。
补了一条「**无错误、只是提前到终点**」的用例才抓住 ——
提醒：给判定逻辑写测试时，要特意造出「其他条件都正常、只这一条不满足」的情形。

### 顺带一条

``Route`` 压测路线必须留 2 倍余量，否则引擎会先到终点、压测提前结束，
而报告里的秒数失去意义。判据是 ``covered_s``（最后一个采样点的时刻）而不是
「墙钟等了多久」—— 后者只会告诉你 sleep 睡够了。

### 实测结果（同日，iPhone 18,1 / iOS 27.0.1 / USB，10.0 km/h @ 1 Hz）

| 项 | 5 分钟 | 10 分钟（正式） |
| --- | --- | --- |
| 注入成功 | 300 点 | **599 点** |

## F16 ★ 30 m 的圈与 3 km 的目标：解法是把围栏半径与里程**解耦**，但「差几圈」取决于 App 的滤波口径

**涉及**：`src/vrun/route.py`（新增 `circle_points` / `circle_route` / `circle_route_to`）、
`src/vrun/preview.py`（新增）、`src/vrun/cli.py`（`soak --center/--dry-run` 等）、
`tests/test_circle.py`（新增）、`tests/test_preview.py`（新增）

### 背景

用户指定：注入点为**四川大学望江校区体育运动中心** `30.628212, 104.084842`，
「绕着他跑个 30 米直径的圈。圈小点，定位要准确，**免得超出电子围栏**」。

而 §6 M4 的验收目标是 **3 km**。30 m 直径的圈周长只有 **94.25 m** ——
一圈是目标的 1/32。这两个数直接打架。

⚠️ 坐标的**外部交叉验证没做成**：Overpass API 持续 502（服务满载）、
Nominatim 连接超时。于是这个点只以用户提供的值为准，
**没有独立来源证明它确实落在操场上**。这是本条结论的一个未闭合的口子，
如实登记。

### 解法：把「圈多大」和「跑多远」拆成两个独立的量

```python
circle_route(center, diameter_m=30.0, laps=34)
```

**同一个圆重复 34 圈，几何完全重合**。手机自始至终只在半径 15 m 内打转，
而里程线性累加到 3.2 km。围栏半径与总里程彻底解耦。

⚠️ 「完全重合」是硬要求。若改成一圈套一圈的螺旋（每圈偏移几厘米），
几何不再重合，「重跑同一个圈」这个前提随之失效 ——
围栏半径要按**外沿**算，不是按圆心算。
`test圈与圈几何完全重合` 就是守这一条。

### 无噪声时的几何保证：跑不出去

顶点严格落在半径 15 m 的圆上，相邻顶点连的是**弦**，而**弦恒在圆内**；
引擎的插值是线性的、永远落在弦上。
所以无噪声时任何注入点的离圆心距离 **≤ 半径**，实测 20 万点采样最远 **15.000000 m**。
这是「免得超出电子围栏」的**几何**保证，与噪声无关。

含噪声（`realistic`，每轴 σ=3 m 的 AR(1) 慢漂移）时实测最远 **21.37 m**。

### ★ App 的距离不是我们的弧长，而且是**两个方向相反**的效应

这是本条最重要的发现，也是最初差点踩进去的坑。

**效应一：噪声让 App 多算。** App 数的是相邻两个注入点的距离，
噪声把点拉开，于是它数出来的**比弧长大**（+0.85%）。

**效应二：弦比弧短，让 App 少算。** 即使噪声关到 0，
App 数的仍是**直线距离（弦）**，我们推进的是**弧长**。
10 km/h、15 m 半径、1 Hz 时每步跨 2.78 m ≈ 10.6°，弦/弧 ≈ **0.99857**（−0.14%）。

**效应三：低通滤波让 App 大幅少算 —— 而且在 30 m 的圈上格外狠。**

一圈周期只有 **33.9 s**。任何滑动平均都会把圈「缩小」（sinc 衰减）：

| App 的平滑窗口 | 32 圈时 App 数出的距离 | R1（≥ 3 km） |
| --- | --- | --- |
| 3 s | 3080.0 m | ✓ |
| 5 s | 3004.7 m | ✓ |
| 10 s | 2599.7 m | ✗ |

⇒ **按「弧长 ≥ 3 km」定圈数，等于默认 App 不滤波**，而真实 App 几乎都滤波。
这是 32 圈与 34 圈之间那 2 圈的全部来源。

### ★ 余量必须留，而且必须真的算得出来

初版 `plan_laps` 只要 R1「大于 3000」就收手，返回 **33 圈**。
但 33 圈、5 s 窗口下三个种子分别数出 **3004.7 / 2993.0 / 3000.9 m** ——
**正好骑在 3000 线上，换个种子就翻车**。

更糟的是这个「压线」在实现里**根本看不出来**：`margin()` 当时写成

```python
gap / abs(value - lo)      # ← 分子分母是同一个数
```

于是 margin **恒等于 1.0**，「余量 100%」—— 检查在，但**永远不会失败**。
（这条单独立为 F17，因为它和 F11 是同一类病。）

改成**分母用边界自身的量级**（`(value - lo) / lo`）并要求 R1 余量 ≥ 2% 后，
搜索返回 **34 圈**，平滑口径 **3094.1 m**（余量 3.14%），
**5 个种子全部通过**。

### 为什么 R3「最低速度」不能由工具替他猜

逐点口径下最低速度 ≈ 5.95 km/h（33 圈）/ 0.30 km/h（34 圈）——
**同一套参数、只因为采样点多了 30 个就完全不同**。
原因：噪声差分能抵消前进量，采样越密越容易撞到接近 0 的瞬时速度。
平滑 5 s 口径下则稳定在 **3.85–3.91 km/h**，与圈数无关。

⇒ 把 R3 写进圈数搜索会得到一个**无解目标**（跑得越久越不达标），
搜索一路撞到 `max_laps` 上限。实测：该变异下 `plan_laps` 耗时 113 秒、返回 400 圈。

所以 `plan_laps` **只**把 R1 与 R4 纳入条件，R3 明确排除并在报告里如实显示判负。
R3 的口径必须由用户看 App 界面来定。

### 工具：0.2 秒出 18 分钟的结论

`vrun soak --dry-run --center 30.628212,104.084842 --diameter 30 --to-end`

不连手机，跑完假时钟后逐条给出 R1–R5 在**两种口径**下的判定，
外加电子围栏最远距离与平滑窗口敏感性表。
这让「要不要占手机 19 分钟」这个决定可以在**不占**的前提下做出。

⚠️ 预览跑的是**同一个** `TrackEngine` 与**同一份**种子化 `GPSNoise`，
只是把时钟换成假时钟 ⇒ 真机跑出来的轨迹与预览**逐点一致**。
但它**只证明「按这些参数注入会是什么样」，不代表真机注入成功** ——
后者仍然要靠 soak 的四条红线（丢失点数 = 0 / 跑满 / 无报错 / 清理成功）。

### 变异验证

12 组变异全部命中：圆画大 10%、每圈偏移 1 cm（退化成螺旋）、
圈数改用 π·d 估算、余量分母改错、围栏参考系改成路线首点、
箱式平均窗口不强制奇数、两端补零、搜索放弃余量、R3 被写进搜索、
R1/R2 上下界互换、报告漏掉 R3、`--noise` 档位与 `LEVELS` 不同步。

### ★ 真机校准：App 的滤波窗口 ≤ 5 s（2026-10-21）

第 1 轮真机跑挂了，跑到 **1810 m**（12 分 35 秒）时 USB 传输断了。
但**这半个多小时的数据反而校准了 App 的口径** ——
用户报告 App 对这 1810 m **判无效、里程显示「约 1.8 km」**。

对照离线敏感性表：

| App 平滑窗口 | 1810 m 会被数成 | 与「约 1.8 km」符不符 |
| --- | --- | --- |
| 逐点（不滤波） | 1810 m | ✔ |
| 3 s | 1792 m | ✔ |
| **5 s** | **1747 m** | ✔ |
| 10 s | 1513 m | ✘（会显示约 1.5 km，明显偏少） |

⇒ **10 秒窗口被排除** ⇒ App 的滤波窗口 **≤ 5 s**。

这条结论很值钱：它说明「10 s 窗口 ⇒ R1 不达标」那个**最坏情况不会发生**，
而 `plan_laps` 搜圈数时用的正是**保守的 5 秒**口径 ⇒ 34 圈 / 3204 m 的计划站得住。

⚠️ 但「1.8 km」是**约数**，它区分不了「逐点」与「3 s / 5 s」。

**跑完把那个数告诉我，口径就一锤定音了。**

## F17 ★ 「余量恒等于 1.0」：一个永远不会失败的检查

**涉及**：`src/vrun/preview.py`、`tests/test_preview.py`

### 病

`checks()` 给每条规则算「离边界还有多远」，用于自动搜索时判断压线与否：

```python
# 第一版
span = (value - lo)          # 下界规则：span = 当前值 - 边界
gap  = min(value - lo, ...)  # gap  = 当前值 - 边界
return gap / abs(span)       # ⇒ 恒等于 1.0
```

分子分母是**同一个表达式**。所有下界规则的余量都返回 1.0，
「刚好压线」与「超出 50%」在搜索眼里**完全一样**。

### 为什么它特别危险

这个检查**存在、有名字、有测试覆盖路径**——
搜索确实调用了它，测试确实跑过了它，报告里也确实写了余量。
它唯一的问题是**永远不会失败**。

F11（F15 的同类）已经记过一次「静默失效」；这次的教训更细一档：

> **一个检查最危险的形态不是缺失，而是「写了但恒真」。**
> 缺失至少有断点，恒真只会给你虚假的安心。

### 修法与护栏

分母改用**边界自身的量级**：`(value - lo) / lo`。语义是「相对下界的百分比余量」，
无量纲、可跨规则比较。

`test余量用边界自身作分母` 钉住具体数值（3004.7 m 对 3000 m ⇒ 0.157%），
`test压线与稳过必须被判成不同` 钉住语义。
变异测试把分母改回 `1.0`，两条测试立刻变红。

### 同一次修掉的第二例：文档与实现各说各话

`_boxcar` 的注释写「边缘**复制**」，实现做的是「**截断**」。
两种都能工作，但读代码的人会照着「复制」去推算首尾速度
（复制下 `i=0` 是 mean(0,0,0,1,2)=0.6，截断下是 mean(0,1,2)=1.0）。
现已统一为「截断」，并在注释里写明两种的差别。

## F18 ★ `--noise` 的 choices 写了 `strict`，引擎只认 `harsh`

**涉及**：`src/vrun/cli.py`、`tests/test_cli.py`

### 病

`soak` 子命令的噪声档位手写成：

```python
choices=["off", "realistic", "strict"]     # ✗
```

而 `GPSNoise.LEVELS` 的键是 `{"off", "realistic", "harsh"}`。
⇒ `vrun soak --noise strict` **通过 argparse**，几百毫秒后引擎才抛
「未知噪声档位 'strict'，可选：['harsh', 'off', 'realistic']」。

错误信息指向的位置（引擎内部）与真正的原因（CLI 的参数声明）**完全无关**。
其余四个子命令（`estimate` / `golden` / `simulate` / `gpx`）用的是
`sorted(("off", "realistic", "harsh"))`，是对的 —— 只有 `soak` 漂了。

### 修法：从数据源推导，让漂移**不可能发生**

```python
NOISE_LEVELS: list[str] = sorted(GPSNoise.LEVELS)
```

四处 `--noise` 全部改成 `choices=NOISE_LEVELS`。

护栏不是「再写一遍正确的字符串」，而是两条结构性的测试：
`test每个子命令的档位都等于引擎的档位`（比对）+
`test任意档位都能被引擎接受`（**逐个喂给引擎**，非法的会抛）。

### 教训

> **同一个概念在两处列举，就是两处会漂移。**
> 护栏应当是「比对」，而不是「再抄一份」。
> 这与 F14（跨语言协议两侧各写一份 `Decodable`）同源，
> 只是这次漂移发生在同一个语言内部。

## F19 ★ 坐标「不报错，只是偏了」：国内地图给的不是 WGS-84

**涉及**：`src/vrun/geo.py`（新增坐标系换算）、`src/vrun/cli.py`（新增 `geo-check`）、
`tests/test_coord_system.py`（新增）、`tests/test_cli.py`

### 背景

用户在 M4 验收时反馈：「**偏了呢**」—— 望江校区的坐标注入到手机上，落点不对。

用户提出：「检查可能导致 app 内地图选点获取的坐标不准确的状况。」

### 根因：三个坐标系，国内地图给的**不是** DVT 要的那个

| 坐标系 | 谁在用 | 与 WGS-84 的偏移（成都一带） |
| --- | --- | --- |
| **WGS-84** | GPS 原始坐标、**DVT 注入要的就是它** | 0 |
| **GCJ-02**（国测局「火星坐标」） | 高德、腾讯、微信、苹果地图（中国区） | **366 m** |
| **BD-09** | 百度（在 GCJ-02 基础上再加密一次） | **1914 m** |

⇒ 把手机地图上抄来的坐标**直接**当 WGS-84 注入，
落点会偏出去几百米到两公里，而**一切看起来都正常**：
不报错、不崩溃、轨迹漂亮、里程照涨。

这就是「偏了呢」最可能的成因 —— **而且它永远不会自己暴露**。

### 关键澄清：MapKit 本身是安全的

`MKMapView.convert(_:toCoordinateFrom:)` 返回的仍是 **WGS-84** ——
苹果地图（中国区）的底图来自国内供应商（GCJ-02），
但 MapKit 内部对瓦片做了**纠偏**，所以从地图上点出来的坐标是 WGS-84。

⇒ **在 VRun 自己的地图上选点取坐标是安全的**，
从高德/百度抄则必须先换算。这条区分很重要，否则会连 MapKit 一起怀疑。

### 处置

**① `geo.py` 新增坐标系换算**（`wgs84_to_gcj02` / `gcj02_to_wgs84` /
`wgs84_to_bd09` / `bd09_to_wgs84` + 通用入口 `to_wgs84` / `from_wgs84`）。

反算用**不动点迭代**（6 次收敛到 1e-9 度），
不用流传最广的那种「正算一次再减一次」—— 后者的往返误差有 **0.08–2.07 m**，
而这里正是「差几百米」的场合，不该再叠一个不确定量。实测本实现往返误差 **0.0000 m**。

**② 新增 `vrun geo-check` 命令**：把「偏了多少」变成可以对着看的数。

```
$ vrun geo-check --lat 30.557533 --lon 103.997792 --system gcj02
输入      (30.557533, 103.997792)  坐标系 gcj02
WGS-84    (30.560169, 103.995506)  ← DVT 注入要用这个
  wgs84   (30.560169, 103.995506)   与 WGS-84 相差       0 m
  gcj02   (30.557533, 103.997792)   与 WGS-84 相差     366 m ← 你给的就是这个
  bd09    (30.553121, 103.978469)   与 WGS-84 相差    1914 m
```

**③ `soak` 新增 `--coord-system`**：换算在**一处**做完，
往下传的（预览、路线、注入）全部是 WGS-84 ——
「一半换了一半没换」是最难查的那种错。

### 顺带发现的标准算法细节

`out_of_china` 判据（境外不偏移）**必须**有。
许多流传的拷贝把它写反了（注释说「True = 境外」，代码却 `return False`）。
本实现按注释语义返回 True，并有用例钉住。

## F20 ★ 缩放绕质心 ⇒ 起点漂 451 m，而界面**不报任何错**

**涉及**：`src/vrun/route.py`（`Route.scaled_to`）、`app/VRun/Sources/VRunApp/RouteModel.swift`
（`scaled(to:)`）、`src/vrun/soak.py`（`make_long_route`）

### 病

`Route.scaled_to()` 与 Swift 侧 `RouteModel.scaled(to:)` 都**绕质心**等比缩放。

而链路上有三件事都指着「第一个点」：

- 绿圈的语义是「路线起点」（`RouteModel.startAnchor`）
- 侧车注入的是 `route.point_at(0)`（`session.prepare`）
- 用户在地图上点的也是第一个点

⇒ 绕质心缩放会把**起点**推走。实测：
画一个 **30 m 直径的圈**再缩放到 **3000 m**，起点漂 **451 m**。

451 m 对 30 m 的圈来说是**十几个圈半径**。而界面上：
路线照常显示、按钮照常可点、注入照常进行、**零报错**。

### 为什么这条特别危险

它不是「某个数字算错了」，而是**语义错位**：
用户以为「我点的那一下」是起点，实际注入的是另一个地方。
而 UI 上没有任何东西能提示这件事 —— 绿圈会跟着缩放后的路线走，
看起来完全正常。

### 修法

缩放锚点从**质心**改成**第一个点**。

`alat + (lat - alat) * factor` 在 `lat == alat` 时**精确**等于 `alat`
（`0.0 * factor == 0.0`），所以锚点在迭代修正中一动不动。

两侧同步改了（这是跨语言契约）：Python 的 `scaled_to` 与 Swift 的 `scaled(to:)`。

`make_long_route()`（压测用的合成方形路线）改成**直接按目标周长构造**，
不再「先画大方块再缩放」—— 否则缩放锚点一改，
整条路线会从 origin 向东偏出几百米，而 origin 是「江安校区附近的合成起点」。

- Python：`test_keeps_start_point_fixed`、`test_start_point_survives_many_scalings`、
  `test_scaled_shape_starts_at_the_anchor`（30 m 圈的具体场景）
- Swift：`testScalingKeepsStartPointFixed`、`testRepeatedScalingKeepsStartPointFixed`
- 变异测试：把锚点改回质心 → 立刻变红

## F21 ★ 12 cm 的偏差：只有「**独立重写一遍标准算法再比对**」才抓得到

**涉及**：`src/vrun/geo.py`（`_gcj_offset`）

### 病

GCJ-02 正算的纬向分母，我写成了：

```python
d_lat = (d_lat * 180.0) / ((_GCJ_A * (1.0 - _GCJ_EE)) / (sqrt_magic * sqrt_magic) * math.pi)
```

而标准算法是：

```python
d_lat = (d_lat * 180.0) / ((_GCJ_A * (1.0 - _GCJ_EE)) / (magic * sqrt_magic) * math.pi)
```

前者是 `(1 − ee·sin²)`，后者是 `(1 − ee·sin²)^³ᐟ²`。差约 **0.08%** ——
听起来微不足道，但在成都一带是 **12 cm** 的纬度偏差。

### 为什么常规测试抓不到

- 往返闭合？**照样闭合** —— 正反两处用同一个错公式，错得一致。
- 偏移量级？**照样对** —— 366 m 与 366.9 m 在「几百米」的断言里没有区别。
- 与自己比？**永远相等**。

**所有「只和自己比」的测试在结构上都不可能发现它。**

### 抓它的是这个

**把标准算法独立重写一遍**（不复用本项目任何一行代码），然后逐点比对：

| 点 | 正算分歧 | 反算分歧 |
| --- | --- | --- |
| 成都江安 | **0.00e+00** | 8.3e-06 度 |
| 北京故宫 | **0.00e+00** | 6.7e-07 度 |
| 东京（境外） | **0.00e+00** | 0 |

正算从 **2.3e-06 度（25 cm）** 降到 **0**，问题定位到「纬向分母的指数」。

### 教训

> **一个只拿自己当标准答案的测试套件，测的是「实现没变」，不是「实现对」。**
> 当实现**转写自某个外部规范**时，必须有一份**独立来源**做交叉验证。
> 哪怕差 12 cm —— 12 cm 在 30 m 的圈上是 0.4 个半径，在 366 m 的偏移上是 3%。

顺带钉了具体数值（`TestGoldenValues`）：
BD-09 的加密本身就含一个大位移，漏掉中间的 GCJ-02 那一步后，
偏移量从 1914 m 变成 2079 m，**仍落在「1800–2400 m」区间内** ⇒
量级断言在方向相反的两个效应面前毫无鉴别力，**必须钉位置**。

## F22 ★ 注入连续超时 ⇒ 整个会话崩掉，没有降级

**涉及**：`src/vrun/device.py`、`src/vrun/session.py`

### 现象（真机）

江安那次 M4 验收跑到 **319 个采样点（320 s）** 后：

```
注入超时 (2.0s, 第 1/3 次)：30.55759,103.99766
注入超时 (2.0s, 第 2/3 次)：30.55759,103.99766
注入超时 (2.0s, 第 3/3 次)：30.55759,103.99766
会话异常终止
```

⇒ 整个 soak 直接崩掉。报告：

```
注入延迟    p50 7 / p90 8 / p99 60 / max 2003 ms（323 次尝试，3 次超时）
清理        已确认
❌ 未通过
```

### 问题不在于「超时了」

在于**超时的处理方式**：

- 单点超时 → 重试 3 次 → 仍失败 → **抛 `InjectionError`，整个会话终止**
- 320 秒的成果、319 个已注入的点，**全部作废**
- 而 2 秒的超时阈值对一次 DVT 往返来说**偏紧**
  （同一批实测 p99 是 60 ms，max 2003 ms —— 也就是说**卡过一次**）

### 该怎么改

1. **超时阈值**要区分「慢」与「卡」：连续 N 次超时才算失败，
   单次超时应重试而不是终结。
2. **超时后应当能继续**：跳过这个点、保留已经跑过的轨迹，
   把「丢点」如实记进报告 —— 报告里已经有 `dropped` 这个位置了。
3. 需要知道的是：那次**为什么**卡住。可能是屏幕锁定、
   可能是 App 抢占、也可能只是 DVT 服务的一次抖动。**目前无数据。**

### 根因（2026-10 定位）—— 两条独立的缺陷叠在一起

**根因 A：2 s 的阈值正好卡在长尾上。**

同一批实测的注入延迟分布是 p50 7 / p90 8 / p99 60 / **max 2003 ms**。
也就是说，那 3 次「超时」里至少有一次其实只跑了 **2003 ms** ——
**慢，但没失败**，却被当成了失败。

⇒ 处置：单次 `set` 的超时阈值 **2 s → 5 s**（2.5 倍余量）。

**根因 B：超时与硬失败没有区分。**

`set_location` 抛 `InjectionError` 时不带任何「为什么失败」的信息，
上层只能一律当致命错误处理。可实际上：

| 失败类型 | 含义 | 正确处置 |
| --- | --- | --- |
| **超时** | 设备多半还连着，只是这一次慢了 | **降级继续**（跳点 + 如实计数） |
| 其他（隧道掉了 / 通道断了） | 重试没有意义 | 立刻失败 |

⇒ 处置：`InjectionError` 增加 `timeout_exhausted` 标记，
由**设备层如实给出**（不让上层去猜异常文本）。

### 为什么「超时」值得降级继续

查 `pymobiledevice3` 的 DTX 实现（`dtx/_sender.py::_wait_for_reply`），
源码注释写明：

> cancelled awaiters leave the Future in place so other waiters can still
> receive the eventual reply.

也就是说 **DTX 层对取消是安全的**，超时不会损坏通道。
更进一步：`_send_message` 是**先写出去再等回执**的 ——
所以超时时那条 `simulateLocationWithLatitude:longitude:` 命令
**很可能已经送到了手机**，只是回执没在 2 s 内回来。
换句话说，**超时 ≠ 这个点没送到**。

### 修法

1. `device.py`
   - `set_timeout` 默认 **2.0 → 5.0**。
   - `InjectionError` 增加 `timeout_exhausted: bool`。
   - 超时耗尽 → `timeout_exhausted=True`；其他异常 → `False`。
2. `session.py`
   - 新增 `max_injection_failures`（默认 5）：**连续**超时多少次才放弃会话。
   - 超时且未达阈值 ⇒ **降级继续**：计数 + 发 `error` 事件
     （code `injection_degraded`）+ 跳过该点，**会话继续跑**。
   - 成功一次就把连续计数**清零** —— 隔一个成功再失败说明设备是活的。
   - 非超时类错误 ⇒ **立刻失败**，不走降级路径。
   - `_inject_timeout()` 改为**严格大于**设备层最坏耗时
     （原来取 `max(最坏, 10.0)`，与最坏**恰好相等** ——
     线程侧会在注入刚要失败时先超时，抛出来的是 `TimeoutError`
     而不是 `InjectionError`，「超时」这个信息就丢了）。
3. `soak.py`
   - 报告新增「降级跳过 N 点」一行 —— **看得见的洞**比崩掉更安全。

### 验收

- Python **464 passed**（新增 10 条）。
- **10 组变异全部命中**（`/tmp/mut_f22.py`）：

| 变异 | 被哪条测试抓住 |
| --- | --- |
| 超时阈值退回 2 s | `test_默认注入超时放宽到五秒` |
| 超时被标成硬失败 | `test_超时重试用尽标记为可恢复` |
| 硬失败被标成可恢复 | `test_硬失败不标记为可恢复` |

| 硬失败也降级 | `test_硬失败立刻终止会话不降级` |
| 阈值多容忍一次 | `test_连续超时超阈值才终止会话` |
| 成功不清零连续计数 | `test_成功一次清零连续失败计数` |

## F23 ★ 坐标系只能靠**外部锚点**判定，不能靠推断

**涉及**：`docs/findings.md`（方法论）、`src/vrun/geo.py`（工具）

### 问题

F19 定了「成都一带 GCJ-02 偏 362 m、BD-09 偏 1893 m」，
但这只是**偏移量**。真正的问题是：

> 用户给的 `30.628212, 104.084842` 属于**哪个坐标系**？

三种可能都活着：它就是 WGS-84；它是 GCJ-02（那真值是 `30.630627, 104.082312`）；
它是 BD-09（那真值在 1.9 km 外，落在**另一个校区**，一眼可排除）。

而「望江首轮用户报『偏了呢』」这句话，只说明**偏了**，
不能说明**往哪偏**——两个假设都是「偏」。

### 为什么不能靠推断

- 望江校区在网上的描述全是「一环路南一段 24 号」这种**地址**，没有坐标。
- OSM / Nominatim / ArcGIS 三条路全部超时或 502 ⇒ 拿不到 WGS-84 锚点。
- 维基百科有「川大望江校区站 30.62759, 104.07307」和
  「四川大学 30.63016, 104.09001」——都是**校园级**的点，
  和体育场差几百米，**没有鉴别力**。

### ★ 判定方法：让地图自己把点画出来

最强的武器不是「算偏移量」，而是**把候选点丢回地图，看它落在哪儿**。

1. 找两个**锚点**（都是国内地图 ⇒ GCJ-02）：
   - 360 地图 `四川大学(望江校区)-运动场` → `30.628807, 104.085013`
   - 360 地图 `四川大学-体育馆` → `30.628681, 104.083689`
2. 把用户坐标按**两种假设**分别打上「卫星/影像底图 + 红色标记」：
   - 假设 A：原样当 GCJ-02 → 标记落在**望江运动场的跑道正中央**
   - 假设 B：换算成 WGS-84 → 标记落在**中兴村职工住宅 47 号楼**
3. 结论：**用户坐标是 GCJ-02**，真值 `30.630627, 104.082312`。

⇒ 这一步把「望江首轮为什么偏」也一并解释了：**偏 362 m，方向西北**。

### 教训

> **偏移量是算出来的，坐标系归属是看出来的。**

- 算偏移量只能告诉你「如果搞错了会偏多少」；
- 看落点才能告诉你「到底搞没搞错」。
- 而**最强的判据是让地图自己画出来** —— 卫星底图上的跑道是客观事实，
  不需要任何「这个 POI 的坐标准不准」的前提假设。

⚠️ 反过来说：**中国地图服务（360 / 高德 / 腾讯）的 POI 坐标一律是 GCJ-02**，
拿它们的数字当 WGS-84 会系统性偏 362 m。

### 顺带确认的一件事

360 地图那条「运动场」POI 的 pin 落在跑道**北端**，
而用户抄的坐标落在跑道**中央** —— 两个 POI 相距 68 m。
**这说明「用户从地图上抄的坐标」与「POI 的官方坐标」本来就会差几十米**，
拿 POI 坐标当「唯一正确答案」去判对错，本身就不可靠。

## F24 ★ 报告谎报「清理已确认」—— 安全红线上的谎报

**涉及**：`src/vrun/safety.py`、`src/vrun/soak.py`

### 现象（2026-10-21 望江真机跑）

那轮跑挂在第 653 个注入点（12 分 35 秒），原因是**USB 传输层断了**：

```
userspace tunnel transport closed (device disconnected?); tearing down
got connection reset in tun-read-fd64:de26:6d6f::2
会话异常终止
vrun.device.InjectionError: 注入 30.63072,104.08238 失败（已重试 2 次）：Channel is closed
```

日志里有两行「清除虚拟定位失败（已吞掉异常…）：ConnectionTerminatedError('Channel is closed')」，
**而报告却写着**：

```
清理        已确认
```

### 问题

「清理其实失败了」被写成了「清理已确认」。两条独立的信息丢失叠在一起：

| 层 | 干了啥 | 后果 |
| --- | --- | --- |
| `DeviceBridge.clear()` | 吞掉异常、返回 `False` | **符合**安全红线（清理动作不许抛异常） |
| `SafetyGuard.acleanup()` | **丢弃** `clear()` 的返回值，无条件 `return True` | 「失败」被改写成「成功」 |
| `RunSession.cleanup()` | 原样转交 `cleared=True` | 继续往上骗 |
| `soak` | `rep.cleared = True` | 报告写「清理 已确认」 |

⇒ **手机可能还卡在注入位置上，而报告说没事。**
这是 F15（「压测工具本身会骗人」）的同一个家族，但性质更重 ——
F15 骗的是「跑完了没」，F24 骗的是「手机安全了没」。

### 修法

1. `SafetyGuard.acleanup()`：读 `clear()` 的返回值，`False` ⇒ 返回 `False`。
2. `SafetyGuard._cleanup_without_loop()`：同样读 `fut.result()` 的返回值；
   借循环清理返回 `False` ⇒ **转子进程再试**（`panic-clear` 正是为这个场景存在的）。
3. `soak.py`：清理没确认时，把**原因**带进报告
   （设备层把异常吞进了 `DeviceStatus.error`，不去读它，
   报告就只剩一句「未确认」，人不知道该往哪查）。

### 验收

**4 组变异全部命中**：

| 变异 | 被哪条测试抓住 |
| --- | --- |
| 保险不再看设备层的返回值 | `test_clear_returning_false_is_reported_as_failure` |
| 同步路径又丢掉返回值 | `test_sync_cleanup_reports_failure_when_clear_returns_false` |
| 报告不再带清理失败的原因 | `test清理失败要如实报出来` |
| 压测无条件报告清理已确认 | `test清理失败要如实报出来` |

### 顺带查清：隧道为什么断

`pymobiledevice3` 的 `userspace_tunnel.py::_watch_transport_closed` 的 docstring 写得很直白：

> Tear the tunnel down when its outer transport dies
> (e.g. **the USB cable is pulled**: usbmuxd closes the CoreDeviceProxy connection…)

而事后 `panic-clear` 第一次报 `No such service: com.apple.instruments.dtservicehub`
（该服务**只在设备解锁时**存在），再试就成功了。
⇒ **最可能是 iPhone 自动锁屏导致开发者服务被挂起、USB 传输随之断开**。

⚠️ 仍未定论。下一轮必须先把「自动锁定」设成「永不」。

## F25 ★ 报告的「计划」数字取错了基数

**涉及**：`src/vrun/soak.py`

### 现象（同一轮真机跑）

```
产出采样    653 点
轨迹长度    计划 5460.3 m / 实际 1810.1 m
```

而真实路线只有 **3204.4 m / 1154 个点**（34 圈 × 94.25 m，10 km/h）。
进度条也一直显示「…630/1966 点（32%）」—— 其实当时已经跑过半。

### 根因

CLI 的到点模式把 `duration_s` 传成**引擎超时上限**，不是计划时长：

```python
budget = route.length() / (speed / 3.6) * 1.6 + 120.0     # 1965.8 s
```

而 `soak()` 一律拿 `duration_s` 当计划时长的基数：

```python
rep.planned_samples = int(duration_s * sample_rate_hz) + 1      # 1966 ❌
rep.planned_s = speed_kmh / 3.6 * duration_s                    # 5460.3 ❌
```

⇒ 定时模式没问题（那里 `duration_s` **就是**计划时长），
到点模式全线偏 1.6 倍。

### 修法

按模式取基数：

- 定时模式：照旧按 `duration_s` 算。
- 到点模式：距离 = **路线长度**，时长 = **闭式解 ETA**（与面板同一个函数）。

### 验收

**3 组变异全部命中**：计划距离退回用 `duration` 算 / 计划点数退回用 `duration` 算 /
定时模式被改成按路线长度算。

### 为什么这条值得单独记

> **「超时上限」和「计划」是两个不同的数，被同一个变量装了很久。**
> 定时模式里两者相等，所以错的地方**永远不会在定时模式里暴露** ——
> 只有到点模式才露馅，而到点模式正是 M4 验收要用的那个。
